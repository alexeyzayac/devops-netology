## Задача 1: API Gateway 

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

### Решение:

| Решение | Маршрутизация по конфигурации | Аутентификация | Терминация HTTPS | Особенности |
|---------|-------------------------------|----------------|------------------|-------------|
| **Kong** | Да (через Admin API или декларативные файлы) | Отлично: JWT, OAuth2, Key-Auth, LDAP и др. | Да | Богатая библиотека плагинов, требуется БД (или DB-less режим) |
| **NGINX** | Да (ручное написание `.conf`-файлов) | Слабо: только Basic Auth; для JWT/OAuth2 нужны доработки | Да (эталонно) | Высочайшая производительность, но конфиги менять вручную и перезагружать |
| **Traefik** | Да (автоматически для Docker, Kubernetes) | Хорошо: Basic, Digest, JWT, ForwardAuth (встроенные middleware) | Да (автоматические сертификаты Let's Encrypt) | Низкий порог входа в контейнерных средах, динамическая конфигурация |
| **Yandex** | Да (на основе OpenAPI-спецификации) | Да (интеграция с Yandex IAM и Cloud Functions) | Да (управляется платформой) | Serverless, не требует администрирования, но привязывает к конкретному облаку |

### Выбор: Kong 

1. Он полностью закрывает все три требования:
* маршрутизация настраивается гибко;
* аутентификация поддерживается из коробки (JWT, OAuth2, ключи);
* терминация HTTPS есть.
2. У него много готовых плагинов – не нужно писать код для каждой новой функции.
3. Он не привязан к облачному провайдеру – можно развернуть где угодно (свой сервер, любое облако).

#### Почему не другие?

* **NGINX** – слишком сложно добавлять аутентификацию, придётся много дорабатывать вручную.
* **Traefik** – хорош для контейнеров, но у него меньше возможностей именно для управления API (нет такой экосистемы плагинов).
* **Yandex** – удобно, но если потом захотим переехать в другое облако или на свои серверы, придётся всё переделывать.

**Итог:** Kong даёт лучший баланс между функциональностью, гибкостью и независимостью от поставщика.

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

### Решение:

| Критерий | RabbitMQ | Apache Kafka | ActiveMQ Artemis | NATS (с JetStream) |
|----------|----------|--------------|------------------|---------------------|
| Кластеризация (надёжность) | Да (зеркалирование очередей) | Да (эталонная репликация) | Да | Да |
| Хранение на диске | Да (постоянные очереди) | Да (основной режим) | Да | Да (только в режиме JetStream) |
| Скорость работы | Высокая (до 100000 сооб/сек) | Очень высокая (миллионы сооб/сек) | Средняя/Высокая | Экстремальная |
| Любые форматы | Да (бинарные данные) | Да (Avro, Protobuf) | Да (JMS) | Да |
| Разделение прав | Да (пользователи, vhosts) | Да (ACL, SSL) | Да (JAAS, ACL) | Да |
| Простота эксплуатации | Очень высокая (удобный веб-интерфейс) | Сложная (нужен ZooKeeper/KRaft, настройка партиций) | Высокая | Высокая (лёгкий запуск) |

### Выбор: RabbitMQ

1. Идеальный баланс. Он даёт и высокую скорость (хватит для большинства задач), и надёжность (пишет на диск, кластеризуется).
2. Очень прост в работе. У него лучший веб-интерфейс для мониторинга, его легко настраивать и обслуживать.
3. Безопасность из коробки. Легко разграничить доступ через пользователей и виртуальные хосты (vhosts).
4. Гибкий. Принимает любые форматы (JSON, бинарные файлы и т.д.).

#### Почему не другие?

* **Kafka** — слишком сложна в управлении, её используют для потоков данных и логов, а не для простых очередей задач.
* **ActiveMQ** — медленнее RabbitMQ и уступает в удобстве.
* **NATS** — быстр, но у RabbitMQ экосистема намного больше (легче найти ответы на проблемы и интеграции).
