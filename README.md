## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

### Решение:

**Использовать GitLab как единую облачную платформу для хранения кода, автоматической сборки, тестирования и развертывания.**

Соостветстие требованиям:
* GitLab работает в облаке и уже имеет встроенный Git-репозиторий.
* Для каждого микросервиса заводим отдельный репозиторий.
* Сборка стартует автоматически при push, создании merge request или тега.
* Можно вручную запустить пайплайн с нужными параметрами.
* Используем переменные окружения, которые можно задать на уровне проекта, группы или самой сборки.
* Создаём общие YAML-шаблоны, чтобы не дублировать код для похожих сервисов.
* Всё хранится в зашифрованных CI/CD переменных, доступ к ним строго ограничен.
* Можно описать несколько разных job и использовать разные CI-файлы для разных веток.
* Пишем любые команды прямо в пайплайне.
* Для каждого задания указываем свой образ.
* Ставим своих GitLab Runner на свои сервера, чтобы сборка шла в нашем контуре.
* Настраиваем параллельное выполнение job, а тесты можно разбивать на несколько частей и запускать одновременно.

**Почему именно GitLab CI/CD:**

1. Не нужно связывать отдельные системы для кода, CI и CD. Меньше интеграций – меньше проблем.
2. Конфигурация описывается в одном файле .gitlab-ci.yml, который лежит рядом с кодом. Всё прозрачно и версионируется.
3. Легко использовать свои раннеры, свои образы, любые скрипты. При этом облачная версия избавляет от головной боли с обновлениями и бэкапами.
4. Раннеры можно развернуть в Kubernetes или просто на нескольких VM, что даёт возможность запускать десятки сборок одновременно.

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

### Решение:

**Использовать связку ELK (Elasticsearch, Logstash, Kibana) и FileBeat.**

Соостветстие требованиям:
* FileBeat собирает логи со всех хостов и отправляет в Elasticsearch (центральное хранилище).
* Приложения просто пишут логи в stdout/stderr. FileBeat сам подхватывает их, ничего менять в коде не нужно.
* FileBeat хранит состояние прочитанных логов и при временной недоступности Elasticsearch буферизирует данные на диске, а после восстановления отправляет всё без потерь.
* Kibana даёт удобный интерфейс с мощным поиском по любому полю, фильтрами и регулярными выражениями.
* Kibana готовый веб-интерфейс, где разработчики могут искать логи, строить дашборды и просматривать события.
* Kibana можно сохранить любой запрос и поделиться прямой ссылкой.

**Почему именно ELK:**

1. Elasticsearch (хранилище), Kibana (UI) и FileBeat (сборщик) – это решение, которое легко развернуть в облаке или на серверах.
2. FileBeat гарантирует, что логи не потеряются даже при сбоях сети или хранилища.
3. Kibana интуитивно понятен, позволяет быстро искать ошибки, строить графики и делиться результатами.
4. У ELK огромное сообщество, много готовых решений и документации, что ускоряет внедрение и решение проблем.

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

### Решение:

**Использовать связку Prometheus (сбор и хранение метрик) и Grafana (визуализация и дашборды), дополненную стандартными экспортёрами:**

* **Node Exporter** – для метрик хостов (CPU, RAM, диск, сеть),
* **cAdvisor** – для метрик потребления ресурсов контейнерами (если сервисы запущены в контейнерах),
* **клиентские библиотеки Prometheus** – для экспорта специфичных метрик самого приложения (например, число запросов, время ответа, размер очереди).

Соостветстие требованиям:
* На каждом хосте запускается Node Exporter, который открывает HTTP‑эндпоинт. Prometheus периодически опрашивает эти эндпоинты (pull‑модель) и забирает метрики в своё хранилище.
* Node Exporter предоставляет все стандартные метрики использования процессора, памяти, дискового пространства и сетевых интерфейсов.
* Если сервисы работают в контейнерах, cAdvisor собирает метрики по каждому контейнеру (CPU, память, диск, сеть). Для сервисов без контейнеризации можно использовать аналогичные экспортёры или встроенные средства.
* Разработчики интегрируют в свой код клиентскую библиотеку Prometheus и определяют собственные счётчики, гистограммы и датчики. Эти метрики становятся доступны по эндпоинту /metrics, который также опрашивает Prometheus.
* Grafana предоставляет вкладку Explore, где можно писать запросы на языке PromQL. PromQL позволяет фильтровать, агрегировать, группировать и выполнять математические операции над метриками в реальном времени.
* Grafana – мощный инструмент для построения дашбордов. Можно создавать графики, таблицы, тепловые карты, статистики, а также настраивать оповещения. Дашборды можно сохранять, экспортировать в JSON и хранить в системе контроля версий.

**Почему именно Prometheus + Grafana:**

1. Гибкость сбора метрик приложений – клиентские библиотеки позволяют разработчикам экспортировать любые бизнес‑метрики, не завися от инфраструктурных ограничений. Это критично для микросервисов, где важно отслеживать специфичные показатели.
2. Мощный язык запросов (PromQL) – он даёт возможность строить сложные агрегации и вычисления прямо при запросе, что необходимо для анализа производительности и выявления аномалий.
3. Лучшая визуализация – Grafana предлагает огромное количество типов панелей, поддержку нескольких источников данных (можно объединять метрики из Prometheus и Elasticsearch на одном дашборде), а также простой способ делиться дашбордами и ссылками на конкретные графики.
4. Pull‑модель – Prometheus сам забирает метрики, что упрощает обнаружение сервисов и делает систему более устойчивой к перегрузкам.
